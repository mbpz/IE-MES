## 已知边界和后续风险

1. 原仓库有 12 个 Controller 指向不存在的 JSP，且用户确认没有旧 Eclipse 工作区或备份。现在 12 个入口均可用，其中 ERP/交付和六个生产工位依据现有数据模型重建；无法证明与未知的历史页面交互完全一致。ERP 未配置外部系统接口，交付台账不自动扣库存或改变工单状态，四类新工位事件不改变核心生产状态。这些边界是设计决定，详见各重建文档。
2. 旧 `/install.shtml` 处理器依赖仓库不存在的 `intall.sql`，管理员访问仍返回 404。Docker 初始化不依赖此入口，已限制为管理员路径；在缺少原脚本的条件下未伪造安装器。
3. 旧 `ly_res_roles` / `ly_role_res` 路径缺表但没有发现活跃 Java 调用；未创建推测性的旧表。历史种子库有不良记录缺同站点代码关联，旧记录详情可能只显示页面骨架；新建完整关联的不良流程已在隔离库验证，主库历史记录未补造。详见 [database-gaps.md](database-gaps.md)。
4. 旧 MyBatis 插件仍使用字符串拼接构造部分 SQL 值；本次只修复保留字列名，不把这一兼容性修复误称为 SQL 注入治理。权限已按当前菜单与主要业务 API 验证，但未穷尽每个路由、角色和输入组合。全量安全改造需要单独范围和回归测试。
5. 站点 `*` 的原始工序种子缺少 `default_resource`，因此主库按资源产能报表为 0 行；隔离库补关联后返回 2 行，功能分支可运行。此为样例数据缺口，未改动主库工艺参数。

终验只清理 `ie-mes-final-acceptance` 隔离项目的容器和卷；主项目数据库、上传、配置卷不得执行 `down -v`。参见 [docker.md](docker.md) 中的日常操作和备份恢复步骤。
